## 5. Core positioning / comparison talking points

### vs. Codecademy / freeCodeCamp
- Both are interactive, neither is gamified in any meaningful sense.
- No streaks with consequences, no leagues, no boss battles.
- No AI-use path — they have AI literacy content but not "learn to build things with AI."
- No career layer that generates an actual résumé.
- Cantrip's free tier is comparable; Pro is cheaper than Codecademy Pro.

### vs. boot.dev
- Closest competitor on gamification — also has XP, streaks, boss battles.
- Backend-only (Go, Python, CS fundamentals). No AI path, no web, no SQL for analysts.
- $399/yr. Cantrip is ~$108/yr annual (roughly 73% cheaper).
- No career layer, no résumé export, no job-readiness score.
- On-device AI tutor vs. none.

### vs. Duolingo / gamification comparison
- We get compared to "Duolingo for coding" often. We'll take it.
- Key difference: Duolingo's gamification is famously anxiety-inducing (streak pressure, hard resets). We use streak decay, leniency mechanics, and a repair system.
- Also: Duolingo doesn't have a career layer or an AI path.

### vs. DeepLearning.AI / OpenAI Academy / Anthropic courses
- They teach AI theory and model-specific workflows. Static video + quiz format.
- No gamification, no progression system, no career layer.
- Cantrip teaches how to USE AI tools in real workflows, interactively, with XP.
- Complementary, not competing — but Cantrip is the one you'll finish.

### The honest caveats (say these before someone else does)
- We're newer and have a smaller course library than Codecademy or freeCodeCamp.
- AI content ages fast. We frame lessons around workflows, not specific model names, and review quarterly.
- The social/multiplayer features (guilds, friend streaks) are best with people you know — the game is thinner solo.
- Backend server-side grading (for more complex projects) is on the roadmap; today everything runs client-side.

## 6. OG / meta gaps audit

*Observed during the launch-kit research pass. Report only — no app files were edited.*

### Gap 1 — Homepage has no per-page OG image override
`src/app/page.tsx` exports a `title` and `description` but no `openGraph` block. The root layout fallback fires (`/api/og?title=Cantrip&subtitle=Learn+to+code,+one+spell+at+a+time.`). That generic card is weak for the most-shared URL on launch day.

**Fix:** Add an `openGraph` block to `src/app/page.tsx` with a custom OG image that references the homepage's actual headline ("Learn to Code & Land the Career, Gamified") and a stronger subtitle. The `/api/og` endpoint already supports this; it just needs to be called explicitly with launch-day copy.

### Gap 2 — Several high-traffic public pages have no OG block at all
The following pages export a `title` + `description` but no `openGraph` or `twitter` block, so they all fall through to the root layout's generic branded card:

| Page | File |
|---|---|
| `/about` | `src/app/about/page.tsx` |
| `/blog` (index) | `src/app/blog/page.tsx` |
| `/learn` (catalog) | `src/app/learn/page.tsx` |
| `/paths` (index) | `src/app/paths/page.tsx` |
| `/pricing` | `src/app/pricing/page.tsx` |

These are all crawlable, linkable pages. When shared on social they show the same generic Cantrip card. Per-page OG images would significantly improve click-through from social shares.

**Fix pattern** (same for all five):
```ts
openGraph: {
  type: "website",
  title: "<page-specific title>",
  description: "<page description>",
  url: absoluteUrl("/page-path"),
  images: [{
    url: absoluteUrl(`/api/og?title=${encodeURIComponent("...")}&subtitle=${encodeURIComponent("...")}`),
    width: 1200,
    height: 630,
  }],
},
twitter: { card: "summary_large_image", images: [absoluteUrl("...")] },
```

### Gap 3 — App-shell pages are crawlable with no robots: noindex
`/dashboard`, `/career`, `/leaderboard`, `/profile`, `/account`, `/login`, `/shop`, `/achievements`, `/leagues`, `/guilds`, `/events`, `/boss`, `/quests`, `/review`, `/skill-tree`, `/daily`, `/friends`, `/teams`, `/projects`, `/onboarding`, `/refer` — none export a `metadata` object with `robots: { index: false }`. They are "use client" shells with no server-rendered content; Googlebot will crawl them, find thin/empty pages, and waste crawl budget.

**Fix:** Add a `metadata.ts` (or `layout.tsx`) next to each app-shell page with:
```ts
export const metadata: Metadata = {
  title: "Dashboard",
  robots: { index: false, follow: false },
};
```
Because `"use client"` files cannot export `metadata`, the cleanest approach is a thin co-located `layout.tsx` per route group.

### Gap 4 — `/api/og` OG card has no fallback font loading
`src/app/api/og/route.tsx` uses `fontFamily: "sans-serif"` without loading a web font via the `fonts` option of `ImageResponse`. On many social crawlers the fallback system font differs, making the card look inconsistent across platforms.

**Fix:** Pass a loaded font (e.g. Inter or a Google Font subset) to `new ImageResponse(jsx, { width, height, fonts: [...] })`. Next.js's `ImageResponse` accepts a `fonts` array; fetch a WOFF/TTF from a CDN at edge runtime.

### Gap 5 — Certificate OG image uses a relative URL for the `url` field
`src/app/certificate/[module]/page.tsx` line 28:
```ts
url: `/certificate/${module.slug}`,  // relative path
```
The `openGraph.url` field should be an absolute URL. All other dynamic pages use `absoluteUrl(...)` correctly. This one was missed.

**Fix:** `url: absoluteUrl(\`/certificate/\${module.slug}\`)`.

### Gap 6 — `metadataBase` set correctly but `NEXT_PUBLIC_SITE_URL` defaults to placeholder
`src/lib/site.ts` line 9 falls back to `"https://cantrip.dev"` when `NEXT_PUBLIC_SITE_URL` is unset. Until the env var is wired in the deployment environment, all absolute URLs in OG tags and `alternates.canonical` will resolve correctly — but only because the placeholder happens to be the real domain. Before going live, confirm `NEXT_PUBLIC_SITE_URL=https://cantrip.dev` is set in the Vercel environment so the fallback is not load-bearing.

### Gap 7 — Twitter/X `creator` field missing on article pages
Blog post and lesson pages set `twitter.card` and `twitter.images` but do not set `twitter.creator`. Adding `creator: SITE.twitter` on article-type pages enables proper author attribution in Twitter Cards.
